## livox_driver2 点云突发（4s 无输出后一次性吐出）分析与监测

### 流水线线程模型（standalone 版）
SDK 收包线程 → `PubHandler::OnLivoxLidarPointCloudCallback` → 无界 `deque<RawPacket> raw_packet_queue_`
→ `RawDataProcess` 线程 → `LidarPubHandler::points_clouds_`（无界 vector 累积）
→ `CheckTimer()` → `LidarCommonCallback::OnLidarPointClounCb` → `Lds::StoragePointData`
→ `Lds::PushLidarData` → 环形队列（size = 10 或 freq+1 上取到 2 的幂，满则丢且无日志）
→ `Lddc::PollingLidarPointCloudData`（同一线程立即 drain）→ `custom_cb_`。
注意：`PointCloudDataPollThread` 在 standalone 版是空实现，整条链路串行在同一个线程上，
下游回调耗时直接冻结整条流水线。

### 可能憋住 4s 的两个根因
1. `CheckTimer()` 时间同步分支的门控 `recent_time_ms % publish_interval_ms_ != 0`：
   要求最后一点的绝对时间戳毫秒值恰好是发布间隔整数倍。包间隔越大/时间戳不是 1ms 对齐，
   命中概率越低；一旦错过，累积的点云不清空，命中时一次性全吐（典型表现为偶发长静默 + 巨帧）。
2. 下游 `custom_cb_` 阻塞（>4s）导致处理线程冻结，`raw_packet_queue_` 无界积压，
   恢复后同步时间戳模式下会一次性发布积累的全部点云。
3. `Lddc::DistributePointCloudData` 在非 `kConnectStateSampling` 时直接 return 且不 drain，
   若 set_bits 未清零（配置请求失败/超时），会表现为完全无输出。

## CheckTimer 补丁修复（已实施）

### 1. 发布门控：毫秒取模 → 发布槽跨越（pub_handler.cpp CheckTimer）
原：`recent_time_ms % publish_interval_ms_ != 0` 才放行（每个周期仅 1ms 窗口命中，错过就一直累积）。
现：`slot = recent_time / publish_interval_`，`slot > last_publish_slot_[id]` 即放行；
新增 `std::unordered_map<uint32_t, uint64_t> last_publish_slot_`，首帧只记录槽位不发布。
效果：放行不再依赖毫秒对齐，帧边界仍对齐绝对时间轴，杜绝"漏命中→憋 4s→巨帧"。

### 2. 积压切片发布兜底
新增 `LidarPubHandler::ExtractPointsUpTo(cutoff, out)`：二分取出 offset_time <= cutoff 的点，
剩余点保留（points_clouds_ 时间点递增）。当缓存跨度 diff > max_frame_span_ns_(=2*publish_interval_)
时跳过槽位判定、按 publish_interval_ 切片发布，直到追平；两个分支（同步/非同步）都加了保护。
`max_frame_span_ns_` 在 SetPointCloudConfig 里随 publish_freq 计算。

### 3. 消除数据竞争
新增 `GetPendingTimeRange(base, recent, size)` 一次加锁取首尾时间与点数，
CheckTimer 两分支改用它，替换原先无锁的 GetLidarBaseTime()/GetRecentTimeStamp() 分次读取
（后者与 GetLidarPointClouds() 的 swap 竞争）。

### 4. 监测同步更新
SkipReason：`kSlotAlign` → `kSlotNotAdvanced`，新增 `kForceFlush`（切片追赶出帧计数）。
### 编译踩坑
`Gauge` 定义在 `livox_ros` 命名空间（不在 QueueMonitor 类内），外部写 `QueueMonitor::Gauge*`
会报 "does not name a type"。已在 QueueMonitor 内加 `using Gauge = ::livox_ros::Gauge;` 别名解决。

验收看两点：`Dump()` 里 `interval_max_ms` 应稳定在 ~1/freq*1000 ms，不应再出现 4000ms；
`force_flush` 平时为 0，仅在下回调阻塞恢复后短期非零。
